Backend Developer Guide

Complete reference for engineers contributing to inventory-reservation — a production-grade NestJS service that prevents overselling under concurrency using a dual-path Redis + database strategy, circuit breaker, and event-driven architecture.

NestJS 11 TypeORM + PostgreSQL Redis 7 + BullMQ DDD · SOLID · EDA Circuit Breaker Swagger at /api

3 — Dual-Path Concurrency Strategy

Two layers of protection prevent overselling. Redis Lua is the fast path; Mutex + SELECT FOR UPDATE is the reliable fallback when Redis is unavailable.

⭐
Why two layers?

Redis Lua is atomic and fast — ideal for high-concurrency stock decrement. But Redis can fail. When the circuit opens, the fallback uses PostgreSQL's SELECT FOR UPDATE combined with an in-process Mutex to serialise concurrent requests for the same product within a single Node.js process. Together they guarantee no overselling regardless of Redis availability.

4 — Circuit Breaker State Machine

The circuit breaker routes requests away from Redis when it detects repeated failures, then probes for recovery after a 30-second timeout.

stateDiagram — circuit breaker
stateDiagram-v2 [*] --> CLOSED : Initial state CLOSED --> OPEN : recordFailure() × 5\n(FAILURE_THRESHOLD reached) OPEN --> HALF_OPEN : 30s recovery timeout elapsed\n(nextAttemptAt passed) HALF_OPEN --> CLOSED : recordSuccess()\n(probe request succeeded) HALF_OPEN --> OPEN : recordFailure()\n(probe request failed) note right of CLOSED : Uses Redis Lua path note right of OPEN : Falls back to Mutex + DB note right of HALF_OPEN : Allows one probe request\nthrough the Redis path

Application Layer

ReservationService — routing logic

async reserve(dto: CreateReservationDto): Promise<Reservation> {
  if (this.circuitBreaker.isOpen()) {
    return this.reserveWithFallback(dto);   // Mutex + SELECT FOR UPDATE
  }
  try {
    return await this.reserveWithRedis(dto);   // Lua atomic decrement
  } catch (e) {
    this.circuitBreaker.recordFailure();
    return this.reserveWithFallback(dto);
  }
}

Infrastructure Layer

RedisStockService — Lua atomic decrement

-- Atomic: read + compare + decrement in a single Redis operation
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil                    then return -1 end  -- key not seeded
if stock >= tonumber(ARGV[1])      then
  redis.call('DECRBY', KEYS[1], ARGV[1])
  return 1                                           -- success
end
return 0                                             -- insufficient stock

CircuitBreakerService

MethodBehaviour
isOpen()Returns true if OPEN and nextAttemptAt hasn't elapsed. Transitions OPEN → HALF_OPEN silently when timeout passes (returns false to allow probe).
recordFailure()Increments failure count. Opens circuit at threshold. If HALF_OPEN, re-opens immediately.
recordSuccess()If HALF_OPEN, calls reset() → back to CLOSED.
reset()Clears failure count and nextAttemptAt, sets state to CLOSED.

MutexService

Maintains a Map<productId, Mutex>. runExclusive(productId, fn) serialises all concurrent requests for the same product within a single Node.js process, preventing race conditions when Redis is unavailable.

ExpiryProcessor (BullMQ)

@Processor(EXPIRY_QUEUE_NAME)
@OnWorkerEvent('completed')
async process(job: Job<ExpiryJobData>) {
  const reservation = await this.reservationRepo.findById(job.data.reservationId);
  try {
    reservation.expire();        // throws if already CONFIRMED / CANCELLED
    await this.reservationRepo.save(reservation);
    await this.dispatchEvents(reservation);
  } catch (e: InvalidStateException) {
    // Already in terminal state — skip gracefully
  }
}

Concurrency Strategy Deep Dive

Stock formula

availableStock = totalStock − confirmedSales − activeReservations

totalStock is the total units ever added. confirmedSales counts units where payment is finalised. activeReservations counts units currently held (but not yet confirmed or released). This formula guarantees no double-counting across concurrent operations.

Layer 1 — Redis Lua script

Atomic read-compare-decrement in a single Redis command. No round-trips. Ideal for high-throughput concurrent reservation creation. Returns -1 if the key is unseeded (product not in Redis), 0 if insufficient stock, 1 on success.

Layer 2 — Mutex + SELECT FOR UPDATE

When Redis is unavailable (circuit OPEN), a product-scoped Mutex ensures only one coroutine at a time enters the critical section within this Node.js process. Inside the mutex, a SELECT ... FOR UPDATE transaction provides cross-process protection at the database level.

Redis rehydration

When Redis recovers (circuit transitions CLOSED via HALF_OPEN), onRedisRecovery() queries getAllAvailableStock() from the DB and calls setStock() for each product, bringing Redis back in sync with the source of truth.

ℹ️
Why not Redis alone?

Redis can fail, restart, or be evicted. If the counter is lost, the DB is still correct. The fallback path using PostgreSQL's MVCC + SELECT FOR UPDATE is the safety net that ensures no overselling even during Redis outages.

Conventions & Rules

Adding a new domain event

1. Create an event class in src/domain/events/

2. Add it to the Reservation entity's domain events collection in the appropriate transition method

3. Create a listener in src/application/listeners/ decorated with @OnEvent('...')

4. Register the listener in app.module.ts providers

✅
Never modify ReservationService to add side effects

Add a new @OnEvent() listener instead. The service is closed for modification (OCP). The event bus is the extension point.

Repository injection

Repositories are injected by Symbol token (RESERVATION_REPOSITORY, INVENTORY_REPOSITORY), not by class name. This enforces DIP — the service depends on the interface, not the TypeORM implementation.

// In app.module.ts
{ provide: RESERVATION_REPOSITORY, useClass: TypeOrmReservationRepository }

// In reservation.service.ts constructor
@Inject(RESERVATION_REPOSITORY) private readonly repo: IReservationRepository
