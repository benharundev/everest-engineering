Complete reference for engineers contributing to inventory-reservation-client — a React 18 + TypeScript 5 single-page application built on Domain-Driven Design, SOLID principles, and Event-Driven Architecture.

First-time setup

On first load the app reads api_base from localStorage (defaults to http://localhost:3000). Change it anytime in the Settings tab — no restart required.

✅
Seed inventory before creating reservations

The backend's Redis stock counter must be primed first. Open Settings → Seed Inventory and add at least one product. A 409 Conflict on reservation creation means inventory is unseeded.

The dependency rule

Components → Hooks → Use Cases → Domain interfaces. Infrastructure implements those interfaces from the outside. Nothing in Domain or Application ever imports from Infrastructure, Components, or the Events layer. Violations break DIP and must not be introduced.

Domain Layer

The domain layer contains pure TypeScript business rules. No React, no fetch, no localStorage. Every other layer may import from here; this layer imports from nowhere. This is what makes the business logic portable, testable, and framework-agnostic.

Entities

Reservation

A rich entity that owns its own business logic. Components never recompute status or expiry — they call entity methods.

class Reservation {
  // Constructor args — all readonly
  id: string;  productId: string;  productName: string
  userId: string;  quantity: number;  status: ReservationStatus
  expiresAt: Date;  createdAt: Date

  // State queries
  get isActive(): boolean
  get isConfirmed(): boolean
  get isCancelled(): boolean
  get isExpired(): boolean

  // Business rules
  get canConfirm(): boolean   // true only when ACTIVE
  get canCancel(): boolean    // true only when ACTIVE

  // Expiry calculations — used by ExpiryBar
  get expiryPercentElapsed(): number  // 0–100
  get timeRemainingMs(): number       // 0 when expired

  // Immutable status update
  withStatus(status: ReservationStatus): Reservation
}

Inventory

class Inventory {
  productId: string;  name: string;  totalStock: number
  confirmedSales: number;  activeReservations: number;  updatedAt: Date

  get availableStock(): number   // totalStock - confirmedSales - activeReservations
  get isOutOfStock(): boolean
  get isLowStock(): boolean      // availableStock < 5
}

Events (EDA)

The Events layer decouples producers (use cases that mutate data) from consumers (UI side effects like toasts and data refreshes). A use case publishes an event; it has zero knowledge of who is listening.

EventBus

// Subscribe — returns an unsubscribe function
const unsub = eventBus.subscribe<ReservationCreatedEvent>(
  'ReservationCreated',
  (e) => console.log(e.reservation.id)
);
unsub(); // call to unsubscribe

// Publish — dispatches to all subscribers synchronously
eventBus.publish(new ReservationCreatedEvent(reservation, customerName));
ℹ️
Singleton pattern

eventBus is a module-level singleton exported from src/events/EventBus.ts. The DI container imports and passes it to every use case that publishes, ensuring all parts of the app share the same instance.

Handlers

Both handlers are registered once in AppContext on mount and automatically unsubscribe on unmount:

// AppContext.tsx — EDA wiring
useEffect(() => {
  const cleanupToast   = registerToastHandler(toast);
  const cleanupRefresh = registerRefreshHandler(triggerRefresh);
  return () => { cleanupToast(); cleanupRefresh(); };
}, [toast, triggerRefresh]);

To add a new side effect to any existing event — for example, sending an analytics ping when a reservation is confirmed — create a new handler file and register it here. Never modify the use case that publishes the event. That is the Open/Closed Principle.

Infrastructure Layer

Infrastructure adapts the outside world (HTTP API, localStorage) to the domain interfaces. This is the only layer that knows about fetch, HTTP status codes, JSON parsing, or localStorage.

LocalStorageNameStore

Implements INameStore using the userNameMap key in localStorage, persisting a { [uuid]: fullName } JSON map across page reloads. The frontend generates a UUID per reservation so names can be resolved even for reservations created directly via the API (fallback: truncated UUID).

DI Container

src/infrastructure/container.ts is the only file allowed to import both domain interfaces and their concrete implementations simultaneously. It wires everything together once at module load time: 

// container.ts — simplified
const httpClient     = new HttpClient(() => localStorage.getItem('api_base') ?? 'http://localhost:3000');
const reservationRepo = new ApiReservationRepository(httpClient);
const inventoryRepo   = new ApiInventoryRepository(httpClient);
const nameStore       = new LocalStorageNameStore();

export const container = {
  createReservation:  new CreateReservationUseCase(reservationRepo, nameStore, eventBus),
  confirmReservation: new ConfirmReservationUseCase(reservationRepo, eventBus),
  // ... all 6 use cases + SimulationService
  nameStore, // exposed for name resolution in components
};

// Health check helper used by AppContext
export function checkHealth(): Promise<boolean>
✅
Swapping implementations

To use an in-memory repository (for testing), replace ApiReservationRepository with InMemoryReservationRepository in container.ts. Every use case, hook, and component automatically picks up the new implementation — nothing else changes.

Hooks bridge use cases to React state. Each hook calls use cases, manages loading / error state, and returns everything a component needs. Components call hooks only — they never import from container directly (the exception: container.nameStore for name resolution is allowed in components).

Cancellable fetch pattern

All fetching hooks use this pattern to prevent state updates on unmounted components:

useEffect(() => {
  let cancelled = false;
  setLoading(true);

  container.getReservations.execute(params)
    .then((r) =>   { if (!cancelled) setResult(r);         })
    .catch((e: Error) => { if (!cancelled) setError(e.message); })
    .finally(() =>  { if (!cancelled) setLoading(false);   });

  return () => { cancelled = true; };
}, [refreshTick, page, filter]);

DDD
Domain-Driven Design

Business rules live inside Reservation and Inventory entities (canConfirm, expiryPercentElapsed). Repository interfaces are the domain "ports". Components never recompute what the entity already knows.

SRP
Single Responsibility

Each class has one job: CreateReservationUseCase creates. ToastHandler shows toasts. HttpClient sends requests. A change to toast wording never touches the use case.

DIP
Dependency Inversion

Use cases depend on IReservationRepository (interface), not ApiReservationRepository (class). container.ts is the only file that closes this gap. Components depend on hooks, not the container.

OCP
Open/Closed

Add a new reaction to ReservationCreated (e.g. analytics ping) by subscribing a new handler. The use case that publishes is never edited. Existing behaviour is preserved by default.

EDA
Event-Driven Architecture

After any mutation, use cases publish a DomainEvent to the EventBus singleton. ToastHandler and RefreshHandler react independently. Neither the use case nor the component knows what happens after the event is published — they only fulfil their own responsibilities.

How-To Recipes

Add a new tab

1
Add the TabId value

In src/types/index.ts, add your new ID (e.g. 'analytics') to the TabId union type.

2
Create the component

Create src/components/Analytics/Analytics.tsx. Consume a presentation hook. No direct API calls in the component.

3
Register in Sidebar

Add an entry to the NAV array in Sidebar.tsx with your id, label, and icon character.

4
Register in TopBar

Add your tab's title and description to the maps in TopBar.tsx.

5
Mount in App.tsx

Add a render branch for tab === 'analytics' in the conditional block in App.tsx.

Add a new API operation (end-to-end)

1
Add the method to the repository interface

Declare the signature in src/domain/interfaces/IReservationRepository.ts. This is the contract everything else depends on.

2
Implement it in the API repository

Add the HTTP call in ApiReservationRepository.ts. Map HTTP response to a domain entity; map error codes to domain exceptions.

3
Create a use case

Create src/application/use-cases/MyUseCase.ts. It calls the interface. If it causes side effects, publish a domain event at the end of execute().

4
Wire it in container.ts

Add myOp: new MyUseCase(reservationRepo, eventBus) to the container export.

5
Create a presentation hook

Call container.myOp.execute() from a hook. Expose loading, error, and result. The component imports only the hook.

Add a new domain event side effect

1
Create a handler file

Create src/events/handlers/MyHandler.ts. Export registerMyHandler(deps) that calls eventBus.subscribe() and returns a cleanup function.

2
Register in AppContext

Call registerMyHandler() inside the EDA useEffect in AppContext.tsx alongside the existing handlers. Include the cleanup in the return function.

Change the backend URL at runtime

Navigate to the Settings tab and update the API Base URL field. The change persists to localStorage and HttpClient reads it fresh on every request — no page reload required.

Conventions & Rules

TypeScript rules

RuleDetail
Strict mode always onnoImplicitAny, strictNullChecks, noUnusedLocals — all enforced at build time
No anyUse unknown + a type guard instead. If truly necessary, add a comment explaining why.
No ts-ignoreFix the type error — do not suppress it
Explicit callback parameter types.map((r: Reservation) => ...) — implicit any in callbacks is a build error
Remove unused importsnoUnusedLocals is on — unused imports are compile errors

Architecture rules

RuleWhy
Components do not call use cases or HttpClient directlyMust go through a hook — maintains testability and SRP
Domain layer has zero external importsNo React, no fetch, no localStorage — must be portable and framework-agnostic
Only container.ts imports both interfaces and implementationsMaintains the DIP boundary throughout the rest of the codebase
New side effects go in handler files, not use casesPreserves OCP — use cases stay closed for modification
All HTTP through HttpClient.request()Never call fetch() directly — error normalisation and base URL logic live there

Styling rules

Rule
No CSS libraries (Tailwind, styled-components, CSS modules). Use CSS variables + inline styles.
Use utility classes (card, btn, btn-primary, etc.) for base styles; extend with inline styles.
Do not rename or change the colour palette or font stack — they are referenced across every component.
Do not introduce a router library — the tab model is intentionally simple.
Do not add a state management library (Redux, Zustand, Jotai).

Build gate

🚫
npm run build must exit 0 before any commit

Runs tsc (full strict TypeScript) then vite build. Common causes of failure: unused imports, implicit any in callbacks, incorrect type annotation on a setState updater function, or a keyof (T | null) expression resolving to never.
